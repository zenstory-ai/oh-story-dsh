# Agent Note: 游戏区以试玩、创作画布与文稿连接创作循环

Status: implemented

## Problem

用户认可短剧的自然流程、DSH 风格与内容画布后，希望用同样思路设计游戏区，并要求继续打磨细节。现有试玩已经是主角，但设计页偏向文件查看器，试玩反馈和新版本之间的创作衔接不够自然。

## Decision

保留大面积试玩与 DSH 原生会话，用「试玩 / 创作画布 / 文稿」形成不同观察面。画布组织原著、玩法、世界、人物、美术和真实构建关系，不强制用户沿固定阶段前进。试玩笔记关联当前版本和明确上下文；讨论入口保护已有 Chat 草稿。旧试玩在制作中继续挂载，新版到达后由创作者选择何时载入。QA 留在宿主工具与既有验证文件，不新增可见 QA 面板或门禁分数。

生产 GameStudio 接入已批准的原型方向，画布投影真实存在的六类创作文稿、明确人物/世界小节与可玩构建，不复制演示剧情或图片。文稿复用共享人工缓冲区、DSH 版本保存和冲突恢复。试玩笔记追加到 `PLAYTEST_NOTES.md`，经 DSH 文件系统、安全边界和创建/比较写入前置条件持久化；普通作者 Markdown 不改写，版本散列收进详情。保存期间继续输入的新草稿保持。官方草稿初始化接口把上下文带入原生 Composer，不自动发送。

## Alternatives considered

- 直接复制短剧素材生产链：游戏应围绕可玩体验迭代，内容类型与反馈循环不同。
- 全功能场景、对象和事件引擎：超出 DSH 插件边界，已有 Agent 与项目文件足以承载设计与构建。
- 固定流水线与 QA 状态大屏：用户需要自然创作，且项目明确把 QA 留在基础设施。
- 自动刷新或任意历史版本回退：会丢失试玩进度，当前协议也不保证保存历史构建。

## Consequences

生产版本的当前场景识别、任意场景跳转和可回退构建需要额外协议或存储事实，不能从演示自行推定。试玩笔记采用 Markdown 追加记录协议；浏览器只缓存未提交的草稿，不持久化第二套笔记数据库。内置示例保持只读，反馈可带到 Chat。游戏文稿与笔记支持并发保护，但跨构建的存档兼容与任意版本回退不作承诺。为守住现有 400 KB 浏览器包体限制，esbuild 的发布构建启用完整压缩，保留 sourcemap；未增加依赖或放宽预算。
